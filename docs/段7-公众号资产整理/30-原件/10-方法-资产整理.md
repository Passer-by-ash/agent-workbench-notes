# 资产整理 · 方式方法

> 这份是**可增长的**：每做一摊资产整理，就往里加。不到推翻的时候不重写。
> 现在只有第 1 版（公众号），以后还会有别的库、别的摊子。
> 配套：判据与弯路的**具体条目**在 `00-经验-<摊名>-判据与弯路.md`；本件管**怎么做事**，那份管**这次学到了什么**。

---

## 一、开工前先定三件事

开工不先做，后面必然返工。

### 1. 这份资产是什么（不是「有什么」）

先写清「它是什么、不是什么」。公众号这摊的教训：

- 「公众文章」＝从发布链接采回来的正式发布稿，**基准**
- 「原始稿」＝写之前的手稿，**是它的前身**
- 「存档妥协件」＝为保存发布内容做的 docx，**不是原始稿**——这个区别一开始没分清，返工两轮

**判据**：能不能用一句话说清它和相邻那一块的区别？说不清就是还没想清。

### 2. 权威源是哪一个

同一批内容可能有好几个来源，**必须先确定哪个说了算**。公众号这摊：

| 源 | 地位 |
|---|---|
| 661 条 CSV 全量清单 | **发布清单的权威**（决定「哪些是发布过的」） |
| 5 张 xlsx（277 条） | 当年手动整理表（决定「当年记了什么」） |
| 公众号原文链接 | **发布时间的权威**（`ct` 字段） |
| 本地 docx | 内容来源，**但不是发布证据** |

**判据**：两个源打架时，能不能立刻说出「按哪个」。说不出来就会来回摇摆。

### 3. 怎么算做完

开工前写下验收标准，否则永远不知道停在哪。公众号这摊最后定的是：

- 数量对得上（清单 661 → 库 716，差 55 篇能逐条解释）
- 断链 0、空目录 0、孤岛 0
- 每个字段都能说出「从哪来」

## 二、动手时的四个动作

### 1. 先摸底，别先动手

先把「现在有什么」摸清楚，再决定改什么。摸的项目固定这几样：

```
文件数、目录数、总大小
每类有多少（按年份/按类型）
有没有 0 字节、空目录、重名、命名异常
索引与实物对不对得上
```

`00-工具/02-查结构.cjs` 就是干这个的。**每摊资产都该有一个这样的脚本。**

### 2. 一次只改一个维度

公众号这摊改过的维度：分类、去重、命名、索引、时间字段、链接关系。

**不要一次改两个。** 例如「去重」和「改名」同时做，出了问题分不清是谁导致的。实测踩过：改名脚本跑了两遍，产生「（2020）（2020）」，同时又漏了 `.md` 扩展名，两个错叠在一起排查了半天。

**判据**：出问题时能不能一句话定位到「是哪个动作造成的」。不能就是一次改多了。

### 3. 每一步都要能回退

- 改之前先备份到 `_tmp/备份-<动作>-<日期>/`
- 备份要能直接拷回去用（不是只有文件列表）
- 干跑一次再真跑

**公众号这摊的教训**：最后把 1.4G 过程备份全删了，只留一个 780K 的整库压缩包。当时判断「已经全绿了不需要回退」，但审查报告指出「当前状态没有中间版本可回退」。后来那个压缩包移到了 `90-其他\_备份\`。

### 4. 每做完一步就自检，不留到最后

自检固定五项（对应 `00-工具/01~03`）：

| 检查 | 期望 |
|---|---|
| 断链 | 0 |
| 空目录 / 孤儿 assets / 坏引用 | 0 |
| 孤立文件 | 0 |
| 缺索引 | 0 |
| 命名异常 / 无扩展名 | 0 |

**留到最后一起查＝查不出来源**——五个问题混在一起，不知道是哪个动作造成的。

## 三、判据的写法

这条是从外部检索学来的，也是这次最值钱的一条。

### 判据要写成「能反驳的形式」

| 写法 | 好/坏 |
|---|---|
| 「发布时间以公众号为准」 | ❌ 不可反驳，等于没说 |
| 「发布时间只认链接里的 `ct` 字段，不从文件名/mtime/回看日期倒推」 | ✅ 能说清「什么算违」 |
| 「原始稿要和发布版对上」 | ❌ |
| 「判原始稿去向：同名或同日唯一→就是它；覆盖率≥0.7→改写；...；都不成立→未发布」 | ✅ 按顺序能落到唯一结论 |

**判据不是「原则」，是「决策树」**——拿到一个具体情况，按它走能得出唯一答案。

### 判据和明细要分开存

这次最重要的一条。参见 `00-经验-公众号整理-判据与弯路.md` 开头。

- **判据**：换个库、换批数据照样成立 → 留
- **明细**：哪 42 组、哪 55 篇、匹配率 0.83 还是 0.81 → **不留**

理由（外部检索三条来源都指向同一件事）：**同样的题型改一下数据就不一样了**，明细的复用价值接近零，留着只占地方。而且——把明细移到 archive 不减总量，要减就真删。

### 判据被推翻时怎么办

**补一条更正，不删旧的。** 公众号这摊的「原始稿判据」被用户纠正三次：

1. 第一版：写作日 vs docx mtime 差 60 天 → 错
2. 第二版：文件年份 ≤ 写作年 + 3 → 还错
3. 第三版：读 docx 内部 `dcterms:created` → 对

三次都留着，因为**错误的方向本身是信息**——下次遇到类似判据，会先问「这是不是又一个代理指标」。

## 四、时间与来源

这条几乎每摊都会撞上。

### 时间字段必须有出处

- 每个时间字段旁边要有 `时间来源:`
- 来源分三类：**原文抓取**（可靠、有秒）／**表格记录**（分钟级）／**推测**（不许写）
- **推测的时间宁可不写**——写上去以后会被当成事实继承下去

**反例**：这次有 55 篇的正文写着「取自公众号原文 ct 字段」，但秒位是 00。审查报告判「抄了清单」，我重抓后判「定时发布的真实特征」。**不管哪边对，问题都出在「没有逐篇核过就写了出处」。**

### 秒位、精度这些细节要看分布，不要看单点

审查报告用「秒位 00 有 94 篇，随机应约 12 篇」推断「这批不是真 ct」。方向对（确实不随机），结论错（不是抄清单，是定时发布）。

**方法**：看到分布异常，先问「有没有系统性原因」，再问「是不是造假」。微信定时发布就是系统性原因。

## 五、命名与索引

### 名字要带「是什么」

- 索引必须带库名与颗粒度：`00-索引-公众文章-2019.md` 而不是 `00-索引-2019.md`
- **同名文章必须加区分后缀**（用「（年-月）」不是「（年）」，同年可能有多篇）
- 文件名不能有 `[` `]`（破双链）、不能有零宽字符（看不见）

### 每个目录都要有索引

- 年有年索引，月有月索引，根有总索引
- **索引要能点进去**（用双链，不是纯文本列表）
- 索引条目要带**日期**（`MM-DD HH:MM`），只写 `HH:MM` 定位不到哪天

### 索引必须能和实物对上

**公众号这摊反复栽过**：文件名改过（去重、去零宽、去后缀）之后，索引还指着旧名。

**做法**：索引永远**从磁盘扫出来重建**，不要手写，也不要在改名后只改索引不改正文。

## 六、新旧版本

### 「新版本在用」的旧件怎么处理

- 旧件不放前台（会误导），也不能直接删（可能有人引用）
- 移 `90-其他\_archive\` 或 `_备份\`
- **移之前先查引用面**：谁还指着它

### 过程件

- 中间脚本、dump、临时数据 → `_tmp/`，**跑完即收**
- 有用的脚本沉进 `00-工具/`，其余删
- **过程备份不长期留**：留一个整库快照即可

## 七、收口

### 收口前必须过的几关

1. 五项自检全绿
2. 每个字段能说出出处
3. 数量差能逐条解释
4. 有一个人能看懂的地图（`00-总览.md`）
5. **判据与弯路已经提出来**

### 关于「交接件」

**没有明确的下一班，就不该有交接件。** 公众号这摊最后撤掉了 `00-交接/`——四件交接的「下一班要接的」写的都是同一拨已办完的事。

判断：**交接件的前提是「有人要接」**。没有接件方，写交接件就是给自己看的过程记录，那就该叫「记录」不是「交接」。

### 收口留什么

| 留 | 不留 |
|---|---|
| 总览（地图） | 四件交接的明细 |
| 总结（发生了什么） | 逐篇的匹配率 |
| 判据与弯路 | 哪一组是哪一组 |
| 专档（真实边界，如 39 篇无链接） | 一次性脚本 |
| 工具脚本 | 中间 dump |
| 整库快照（1 个压缩包） | 12 个过程备份 |

## 八、外部同类做法（2026-11-25 检索）

做公众号归档这件事，外面已有成熟工具，我们的做法和它们的对应关系：

| 工具 | 它做什么 | 我们做了什么、差在哪 |
|---|---|---|
| [MagicMD](https://pypi.org/project/magicmd/0.1.1/) | 链接→Markdown 内容包，含 `metadata.json` / `extraction-report.json` / images | 我们手工做了同样的落盘，但**没有转换报告**这一层。它的 `extraction-report.json` 思路值得学：每篇都留「抓取时发生了什么」 |
| [wechat-notebank](https://www.npmjs.com/package/wechat-notebank) | 用本机 Chrome 抓，**自动按真实发布日期命名**，写 Frontmatter，图片落 `.assets` | 命名与 `.assets` 结构**和我们一模一样**。它多做了「Excel 批量导入」——正是我们从 F 盘 xlsx 起手的活 |
| [wechat-article-exporter](https://zhuanlan.zhihu.com/p/1999103970044581595) | 走公众号后台搜索接口，批量抓全部文章，多格式导出 | 它要公众号后台权限；我们没这个条件，只能走公开链接 |
| [obsidian-wechat-sync](https://github.com/Lizhen0628/obsidian-wechat-sync) | Obsidian 插件，**按 YYYY-MM 归档**，图片本地化 | 年月分目录的做法和我们一致 |

**结论：归档动作本身别人都做过，我们没做的创新。** 真正有差别的只有三处：

1. **三层结构**：公众文章 / 原始稿 / 回顾。别人的工具只处理「文章」这一层，没有「手稿」和「后来回看」这两个维度。
2. **去重用的是解析后的 `ct` + 标题**。工具普遍按 URL 或标题去重，遇到长短链同一篇会重复入库。
3. **时间字段带出处**。工具里没见谁标「这个时间是原文抓的还是表格抄的」。

**可借鉴但没做的**：转换报告（每篇留一份「抓取时发生了什么」）。这次 4 篇取不到 `ct` 就是靠人工记的，如果有报告层，会自然留下。

## 九、怎么往上加

下一摊资产整理时：

1. 开工前读一遍本件
2. 做完后，**只加不加**：新判据写进 `00-经验-<新摊名>-判据与弯路.md`，新的「怎么做事」写进本件对应章节
3. 本件第 N 版时，如果某章已经明显不适用，**改那一章**（写明「第几版改的、为什么」），不要重写整份

**别让它变成「什么都往里塞」的文档。** 判据进经验件，方法进本件，状态进总览。三份各管一件事。
